## Phase 1: API Layer
**Goal:** Wrap the pipeline in FastAPI. CLI still works. Tests pass.

### Files to create
- `src/api/app.py` — FastAPI application factory
- `src/api/routes/analyze.py` — analysis endpoints
- `src/api/routes/health.py` — health + readiness probes
- `src/api/middleware/auth.py` — API key validation middleware
- `src/api/middleware/tenant.py` — tenant ID extraction and validation
- `src/api/deps.py` — FastAPI dependency injection (DB session, tenant context, vault client)

### Endpoints

```
POST /api/v1/analyze/event
  Body: AnalysisRequest (trigger="soar_claim")
  Auth: Bearer token (per-tenant API key, validated against Key Vault)
  Returns: { request_id, status, report_url } — async, 202 Accepted
  
POST /api/v1/analyze/batch
  Body: AnalysisRequest (trigger="batch_auto_closed" | "batch_shift_end")
  Auth: Service principal token (internal only, not exposed to SOAR)
  Returns: { batch_id, event_count, status }

GET /api/v1/report/{request_id}
  Auth: Bearer token (same tenant as request)
  Returns: Full AnalysisOutput + report text
  
POST /api/v1/concordance
  Body: AnalystConcordance
  Auth: SOAR service account
  Returns: { recorded: true }

GET /api/v1/health
  No auth — used by Azure load balancer
  Returns: { status: "ok", version, db: "ok" | "degraded" }
```

### Auth design
- Per-tenant API keys stored in Azure Key Vault: `secret/{tenant_id}/purplelens-api-key`
- API key delivered in `Authorization: Bearer <key>` header
- Middleware resolves `tenant_id` from key → injects `TenantContext` into request state
- Service-to-service (batch trigger, SOAR callback): Azure Managed Identity

### Tests required before Phase 2
- `tests/api/test_analyze_event.py` — POST with valid/invalid tenant key
- `tests/api/test_auth.py` — missing key, wrong key, correct key
- `tests/api/test_health.py` — health endpoint returns 200

```python
# Key tables — implement with SQLAlchemy 2.0 declarative style

class Tenant(Base):
    __tablename__ = "tenants"
    id: UUID  # primary key
    name: str
    siem_type: str
    soar_type: str
    active: bool
    created_at: datetime

class AnalysisRun(Base):
    __tablename__ = "analysis_runs"
    id: UUID  # = request_id
    tenant_id: UUID  # FK → tenants.id — ALL queries filter by this
    trigger: str
    analyst_id: Optional[str]
    shift_id: Optional[str]
    status: str  # pending | running | complete | failed
    event_count: int
    llm_tokens_in: int
    llm_tokens_out: int
    llm_cost_usd: float
    prompt_injection_hits: int
    events_quarantined: int
    concordance_recorded: bool
    created_at: datetime
    completed_at: Optional[datetime]

class Finding(Base):
    __tablename__ = "findings"
    id: UUID
    run_id: UUID  # FK → analysis_runs.id
    tenant_id: UUID  # denormalized for row-level security efficiency
    title: str
    summary: str
    severity: str
    confidence: float
    evidence_json: str  # JSON array of Evidence objects
    created_at: datetime

class ConcordanceRecord(Base):
    __tablename__ = "concordance_records"
    id: UUID
    run_id: UUID
    tenant_id: UUID
    analyst_id: str
    llm_guidance: str
    llm_confidence: float
    analyst_determination: str
    concordant: bool
    recorded_at: datetime
```

### Tenant isolation rules
- Every table has `tenant_id` column
- Every query in repos must include `.filter(Model.tenant_id == tenant_id)` — enforced by repo base class
- Row-level security policy on PostgreSQL side as defense-in-depth:
  ```sql
  ALTER TABLE analysis_runs ENABLE ROW LEVEL SECURITY;
  CREATE POLICY tenant_isolation ON analysis_runs
    USING (tenant_id = current_setting('app.tenant_id')::uuid);
  ```
- Application sets `SET app.tenant_id = '{tenant_id}'` at session start

### Tests required before Phase 3
- `tests/db/test_tenant_isolation.py` — verify Tenant A cannot read Tenant B's runs
- `tests/db/test_concordance.py` — insert and query concordance records
- Integration test: full run persisted to PostgreSQL and retrieved correctly

## Phase 3: Async Execution
**Goal:** Analysis pipeline is non-blocking. API returns 202 immediately. Worker completes pipeline async.

### Architecture choice
Use **Celery + Azure Service Bus** (or Redis if Azure Service Bus adds too much complexity for v2).

- API receives request → validates → enqueues Celery task → returns 202 with `request_id`
- Celery worker picks up task → runs full pipeline → writes result to PostgreSQL → updates `status = "complete"`
- SOAR polls `GET /api/v1/report/{request_id}` or receives webhook callback when complete

### Files to create
- `src/worker/celery_app.py` — Celery configuration
- `src/worker/tasks/analyze.py` — `run_analysis_task(request_id, tenant_id)` task
- `src/worker/tasks/batch.py` — `run_batch_task(batch_id, tenant_id)` task
- `src/worker/tasks/notify.py` — `send_soar_callback(request_id, callback_url)` task

### SOAR callback (Stage 3 delivery)
After analysis completes, worker fires:
```
POST {tenant.soar_callback_url}
Authorization: Bearer {tenant.soar_service_token}  # from Key Vault
Body: {
  "request_id": "...",
  "event_id": "...",
  "analyst_id": "...",
  "report": "<full report text for PurpleLens box>",
  "confidence": 0.82,
  "guidance": "Likely Benign"
}
```

### Tests required before Phase 4
- `tests/worker/test_analyze_task.py` — task runs and writes to DB
- `tests/worker/test_notify.py` — callback fires with correct payload (mock SOAR endpoint)
- Load test: 10 concurrent analysis tasks without contention or cross-tenant data access

## Phase 4: SIEM Integration (Live Telemetry Fetch)
**Goal:** Replace file-based input with live SIEM API fetch.

### SIEMClient interface
```python
class SIEMClient(ABC):
    @abstractmethod
    async def fetch_event(self, event_id: str) -> dict:
        """Fetch single event by ID."""

    @abstractmethod
    async def fetch_surrounding_events(
        self,
        event_id: str,
        time_window_hours: int = 72,
        entity_fields: list[str] = None,
    ) -> list[dict]:
        """Fetch events in time window around the triggering event, same entity."""

    @abstractmethod
    async def fetch_entity_history(
        self,
        entity_value: str,
        entity_type: str,  # "ip", "user", "host", "hash"
        days: int = 30,
    ) -> list[dict]:
        """Fetch historical events for an entity."""
```

### Credential management
- Per-tenant SIEM credentials in Azure Key Vault
- Key path: `secret/{tenant_id}/siem-{siem_type}-token`
- `SIEMFactory` fetches credential at request time via managed identity
- Credentials never logged. Token masked in ops context logging.

### Security requirement
- All SIEM API responses pass through `prompt_firewall_event()` before entering pipeline
- This is non-negotiable — live telemetry is more adversarial than file input

### Tests required before Phase 5
- `tests/siem/test_sentinel.py` — mock Sentinel API, verify fetch and normalization
- `tests/siem/test_splunk.py` — mock Splunk API, verify fetch and normalization
- Security test: inject prompt injection string into mock SIEM response, verify quarantine

## Phase 5: Concordance Tracking & Shift Reports
**Goal:** Close the governance loop. Track analyst alignment. Generate shift reports.

### Concordance recording flow
1. Analyst makes determination in SOAR (closes/escalates ticket)
2. SOAR fires concordance webhook to `POST /api/v1/concordance`
3. PurpleLens records: analyst determination vs. LLM guidance → `concordant: bool`
4. Concordance rate aggregated per analyst, per tenant, per shift

### Shift report generation
- Triggered by Azure Scheduler at shift end (configurable per tenant)
- Task queries all runs for the shift window by tenant
- Calculates concordance rate, flags high-concern benign closures
- Generates `ShiftReport` object → persisted to PostgreSQL
- Delivered via: email (SendGrid) + SOAR notification channel

### Concordance-based model quality signal
- If concordance rate for a specific `severity` level drops below threshold (configurable, default 0.75) → alert fires to ops team
- This is the drift detection mechanism: sustained analyst disagreement on a confidence band = model calibration issue

### Files to create
- `src/reporting/shift_report.py` — `generate_shift_report(tenant_id, shift_window) -> ShiftReport`
- `src/reporting/concordance.py` — `calculate_concordance_rate(runs: list) -> float`
- `src/reporting/delivery.py` — email and SOAR channel delivery
- `src/worker/tasks/shift_report.py` — Celery task for shift report generation

## Security Requirements (Non-Negotiable Across All Phases)

These must be validated in every PR:

1. **No hardcoded credentials.** All secrets via Azure Key Vault or environment variables in `.env` (dev only, gitignored).
2. **All telemetry through `prompt_firewall_event()`.** No raw SIEM data reaches `analyze_events()` without sanitization.
3. **All LLM output through `validate_output()` and `validate_semantic_output()`.** No unvalidated model output reaches an analyst.
4. **Every DB query filtered by `tenant_id`.** Repo base class enforces this. Tests must verify cross-tenant isolation.
5. **No LLM determination claims.** `PROHIBITED_PATTERNS` in `security.py` must be extended to cover any new output formats. LLM guides; analyst decides.
6. **Audit log for every analysis run.** `analysis_runs` table is append-only. No updates, only status transitions.
7. **API key rotation.** Per-tenant API keys must be rotatable without downtime (Key Vault versioning).

## What Claude Code Should Ask Before Starting Each Phase

1. **Phase 1 (API):** What SOAR platform is the priority integration target? (Determines webhook payload shape)
2. **Phase 2 (DB):** Confirm Azure PostgreSQL tier and region. Confirm whether row-level security is enabled at DB level or enforced only at application level.
3. **Phase 3 (Async):** Redis or Azure Service Bus as Celery broker? Redis is simpler; Service Bus is more Azure-native.
4. **Phase 4 (SIEM):** Which SIEM first — Sentinel or Splunk? (Drives implementation priority)
5. **Phase 5 (Concordance):** What defines a "shift"? Fixed hours (e.g., 0800-1600) or dynamic by analyst login/logout?
6. **Phase 6 (Deploy):** Single Azure region or multi-region from the start? (Affects PostgreSQL configuration)
