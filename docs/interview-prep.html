The 4 Safety Pillars

Click any pillar to expand. Hover underlined terms for code-level details. Press 1–4 to jump.
01
TREAT THE AI AS UNTRUSTED
We enforced behavior at three distinct layers before any output reached a human — input sanitization, response guardrails, and evidence traceability. Not monitoring. Enforcement.
security-firstsecurity.py

In enterprise, the biggest AI failure mode isn't a bad model — it's trusting the model's output without verification. We built three enforcement layers

The 3 Enforcement Layers
1. prompt_firewall_event() — sanitizes every log field before LLM sees it
2. validate_output() — regex guardrails on raw LLM response text
3. validate_semantic_output() — verifies every evidence citation maps to a real event
before any output reached an analyst.

The prompt injection firewall

prompt_firewall_event()
Recursive tree-walker — checks every dict key and value in every event. Six rules, two actions: redact (sanitize and continue) or quarantine (drop event entirely). Quarantined events never reach the LLM.
walks every field of every log event before the LLM sees it. Live telemetry is adversarial input — a threat actor can embed instructions in log data to manipulate an AI analyzer. We didn't hope the model would resist that. We stripped it before it arrived.

The output policy layer

PROHIBITED_PATTERNS (security.py)
Regex list that blocks the LLM from claiming it: blocked something, removed something, confirmed something definitively, or took any action. Any match → output rejected. This is institutional policy enforced in code.
blocked the LLM from making authority claims — it couldn't say "I have blocked" or "This is confirmed malicious." The LLM guides, the analyst decides.

The semantic validation layer

validate_semantic_output()
Checks every Evidence object: does source_file + record_index actually exist in the loaded event set? If the LLM cited an event that wasn't in the data, the finding is rejected. No hallucinated citations reach analysts.
prevented hallucinated evidence. Every Finding had to cite a real event by file and line number. The schema enforced this: evidence: List[Evidence] with min_length=1.

Input sanitized before the model sees it. Output validated before an analyst sees it. Three enforcement layers — not monitoring, enforcement."

02
STAGE THE ROLLOUT
We ran two retrospective batch phases before going real-time. Each stage proved safety before expanding scope. One client first. Thirty days. Then scale.
deploymentEVOLUTION.md

We didn't go straight to real-time analyst integration. We built a validation ladder

The 3-Stage Deployment Ladder
Stage 1: Batch over SOAR auto-closed events (zero analyst exposure)
Stage 2: Batch over analyst shift determinations (retrospective only)
Stage 3: Real-time per-event on analyst claim (one client first, then scale)
— each stage proving the prior one was safe before expanding scope.

Stage 1

Stage 1 — Batch QA on Auto-Closed Events
Scheduled job ran against SOAR auto-closed events. Zero production risk — if the model was wrong, no analyst had acted on it. Proved pipeline stability under real log diversity. Flagged any high-concern event the SOAR playbook auto-closed incorrectly → T3 alert.
was a scheduled batch job over SOAR auto-closed events. Completely invisible to analysts. If the model was wrong, nobody acted on it. It proved the guardrails held under production log diversity.

Stage 2

Stage 2 — End-of-Shift QA on Analyst Determinations
Ran at shift end over all analyst-marked-benign events. Still retrospective. Generated a shift report for management + detection engineering. Flagged high-confidence discordances for T3 review. Gave detection engineering the first structured daily intelligence brief.
added end-of-shift QA over analyst determinations. Still retrospective — disagreement went into a shift report for management, not a real-time alert to the analyst. Detection engineering used those reports to calibrate SOAR playbooks.

Only after both batch stages validated did we move to Stage 3

Stage 3 — Real-Time SOAR Integration
SOAR webhook fires when analyst claims a ticket → FastAPI endpoint → SIEM API fetches triggering event + surrounding 72h context → ThreatPrism pipeline → report written to PostgreSQL (tenant-scoped) → SOAR pulls report → renders in ThreatPrism box in the ticket UI.
— real-time per-event analysis inside the SOAR ticket. And even then: one client first, thirty days, then expand.

Stage 2 over analyst shift determinations. Only after both proved safe did we go real-time. And even then: one client, 30 days, then scale."

03
MEASURE BEFORE YOU CLAIM
Our governance metric was analyst concordance rate — how often analysts agreed with the LLM's hypothesis. That metric drove model calibration and told us when we had drift before it caused a miss.
governanceV2_SPEC.md

Enterprise AI implementations fail when teams claim outcomes they can't measure. We defined our governance metric

Analyst Concordance Rate
Did the analyst's final determination align with the LLM's hypothesis and confidence score? LLM says "Likely Benign (0.82)" → analyst marks benign → concordance. LLM says "High Concern (0.88)" → analyst marks benign → discordance → T3 flag.
before writing a line of production code: analyst concordance rate.

The LLM expressed a hypothesis with a confidence score

Confidence Score Format
Pydantic schema enforces: confidence: float (ge=0.0, le=1.0). Output examples: "Likely Benign (0.82)", "Possible Lateral Movement — Investigate (0.71)", "High Concern — Escalate Recommended (0.88)". Analyst owns the final call. Always.
. We tracked: did the analyst agree? That metric served three functions: model quality signal, analyst performance signal, and trust calibration over time.

Sustained discordance on a specific event type was a model drift signal

Model Drift Detection via Concordance
If concordance rate for a specific severity band drops below threshold (default 0.75 in V2 spec) → ops alert fires. Means model calibration has degraded on that pattern — before it causes a missed detection. Drives retraining/prompt revision cycles.
— not an analyst problem. That's how we detected degradation before it caused a missed detection.

04
THE AI NEVER OWNS A DECISION
Technical guardrails in the codebase prevented the model from claiming it acted or concluded. The LLM hypothesized. The analyst determined. That boundary was enforced in code, not policy.
governanceadoptionsecurity.py

This was both a security design and an adoption strategy. The PROHIBITED_PATTERNS list

PROHIBITED_PATTERNS (security.py)
Regex patterns that reject LLM output containing: "I have blocked/removed/deleted/remediated", "This is definitely malicious/benign", "System modified/updated/patched", "Confirmed/Certain/Guaranteed that". Any match → output rejected before analyst sees it. Not a prompt instruction — enforced by code.
technically prevented the model from claiming it had taken action or confirmed a threat. Not a prompt instruction — enforced by code.

In the ThreatPrism box

The ThreatPrism Box (SOAR UI)
Text panel inside the SOAR ticket UI, rendered when analyst claims the ticket. Shows: Confidence score + guidance label, Hypothesis, IoCs, Next Steps (how to investigate), Tracking (related events, entity history). Read-only. No buttons, no actions. Analyst reads it, then begins their own investigation.
inside the SOAR ticket, output was always framed as hypothesis and guidance, never conclusion or action. Analysts saw a confidence score and recommended next steps. They made the call.

This is why analysts trusted it. The system never competed with their judgment. It did the T1 groundwork so they could focus on the judgment call itself. That framing drove adoption faster than any mandate could. It also maps directly to NIST AI RMF

NIST AI Risk Management Framework
The AI RMF governs: GOVERN (policies + accountability), MAP (risk identification), MEASURE (metrics + monitoring), MANAGE (response + improvement). ThreatPrism's human-in-the-loop design maps to the MANAGE function: human oversight is the primary control for high-stakes AI outputs in regulated environments.
and meaningful human oversight for high-stakes decisions.

Section 05

Follow-Up Drills

Likely probes after your opening. Short answer always visible. Click for depth.
"How did you handle tenant isolation at the data layer?"▼
Every table had a tenant_id column. Every query filtered by it. PostgreSQL row-level security as defense-in-depth. Per-tenant credentials in Azure Key Vault, never in application code.
Three-layered isolation: application layer (every repo method filters by tenant_id), database layer (PostgreSQL RLS policy — even a bug in app code can't return another tenant's data), and credential layer (per-tenant SIEM/SOAR API keys in Azure Key Vault, fetched via managed identity at request time). Rolled out to one client first — thirty days of clean concordance data — before expanding. The docs/V2_SPEC.md has the exact PostgreSQL RLS policy syntax.
"What happens when the model drifts or starts giving bad guidance?"▼
Analyst concordance rate was our canary. Sustained analyst disagreement on a specific event type meant model calibration had degraded — not that analysts were wrong. That triggered prompt revision or retraining.
We didn't wait for a missed detection. Concordance rate was tracked per confidence band — if "High Concern" calls were consistently being marked benign, that was the signal. In V2 the threshold is configurable per tenant (default 0.75). When it breaks, an ops alert fires. The shift report surfaced this weekly. Detection engineering used it to retune both model prompts and SOAR playbooks simultaneously.
"How did you handle change management and analyst adoption?"▼
We never framed ThreatPrism as replacing analyst judgment. It gave analysts a running start — T1 groundwork done before they began investigating. That framing killed resistance before it started.
Four specific decisions drove adoption: (1) The ThreatPrism box was read-only — no buttons, no actions. (2) Analysts saw a confidence score, not a verdict — "Likely Benign (0.82)" invites agreement or challenge. (3) Stages 1 and 2 were invisible to analysts — by the time Stage 3 launched, management had months of data showing the system worked. Analysts heard "this caught things we missed" before they ever used it. (4) The shift report gave T3 visibility — they became advocates because the system made their oversight work easier.
"How did you handle compliance and data residency?"▼
All AI inference ran through Azure OpenAI Service — Azure-hosted, satisfying data residency for most enterprise contracts. Per-tenant data classification gated what telemetry could leave the client environment.
Azure OpenAI was the deliberate choice over public OpenAI API for exactly this reason — Azure's data processing agreements cover SOC 2 and most GDPR obligations. For clients with FedRAMP or HIPAA requirements, the architecture supports on-premises model hosting because the LLM provider is abstracted in the codebase — swap the endpoint, not the pipeline.
"What was your incident response plan if the AI gave dangerous guidance?"▼
The AI never took action — so the blast radius of bad guidance was bounded by the analyst who reviewed it. The PROHIBITED_PATTERNS layer and human-in-the-loop requirement ensured no automated downstream consequence of a bad model output.
Three containment layers: (1) The model physically cannot claim to have taken action — PROHIBITED_PATTERNS rejects that output before an analyst sees it. (2) Every analysis run is logged to an immutable audit table — trace any bad guidance to specific prompts, events, and model versions. (3) Model versioning meant rollback within one deployment cycle. No autonomous action = bounded blast radius. That's the architectural safety property.
"Walk me through what happens technically when an analyst claims a ticket."▼
SOAR webhook fires → FastAPI validates tenant + authenticates → SIEM API fetches event + 72h context → pipeline sanitizes, correlates, analyzes, validates → report written to PostgreSQL → SOAR pulls report → renders in ThreatPrism box. Target: under 30 seconds.
Full sequence: (1) Analyst clicks "Claim" in SOAR. (2) SOAR webhook fires to POST /api/v1/analyze/event with event_id, tenant_id, analyst_id. (3) FastAPI validates Bearer token against Azure Key Vault, extracts TenantContext. (4) Task enqueued to Celery worker (API returns 202 immediately). (5) Worker calls SIEM API — fetch triggering event + surrounding 72h window. (6) All SIEM data through prompt_firewall_event(). (7) correlate_events() clusters related events. (8) analyze_events() → Azure OpenAI. (9) validate_output() + validate_semantic_output(). (10) generate_report(). (11) Written to PostgreSQL (tenant-scoped). (12) SOAR callback webhook. (13) ThreatPrism box renders in ticket.
